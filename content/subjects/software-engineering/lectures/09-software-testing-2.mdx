## Step 3: independent paths

<Definition term="Independent path">
  A path through the program that introduces <strong>at least one new</strong> set of statements or a new condition. In the flow graph, it moves along <strong>at least one edge not traversed</strong> by the earlier paths.
</Definition>

The **basis set** has exactly $V(G)$ independent paths. Together they make **every statement run at least once** and **every condition evaluate to both true and false**. A basis set is **not unique**: different, equally valid sets exist.

| Program | $V(G)$ | Basis set |
|---|---|---|
| `fun()` (while loop) | 2 | 1-2-4-5 · 1-2-3-2-4-5 |
| `f1(x, y)` (while + if) | 3 | 1-6 · 1-2-3-5-1-6 · 1-2-4-5-1-6 |
| Two-exit `function1` | 3 | 0-5 · 0-1-2-4 · 0-1-3-4 |

## Step 4: deriving test cases

Design one test case per independent path, with inputs that **force** execution along it and the **expected output**.

```python title="f1 is Euclid's GCD by subtraction"
def f1(x, y):
    while x != y:        # node 1
        if x > y:        # node 2
            x = x - y    # node 3
        else:
            y = y - x    # node 4
    return x             # node 6
```

| Case | Path | Input | Expected |
|---|---|---|---|
| 1 | 1-6 | `x = 5, y = 5` | 5 (loop skipped) |
| 2 | 1-2-3-5-1-6 | `x = 10, y = 5` | 5 (one pass through `x = x − y`) |
| 3 | 1-2-4-5-1-6 | `x = 5, y = 10` | 5 (one pass through `y = y − x`) |

For `fun()` the slides use **x = 0** (enters the loop, prints 0–9, y = 13) and **x = 10** (skips the loop, y = 13). To force the second path, `x` must start at 10 or more, so in practice you'd make it a parameter.

### Worked example: shipping charges

<SlideFigure page={14} caption="calculate(amount): 14 nodes, 19 edges and 6 predicate nodes, so V(G) = 7 regions = 19 − 14 + 2 = 6 + 1 = 7." />

```java title="calculate(): node numbers in comments"
public double calculate(int amount) {
    double rushCharge = 0;                              // 1
    if (nextday == "yes") {                             // 1  predicate
        rushCharge = 14.50;                             // 2
    }
    double tax = amount * .0725;                        // 3
    if (amount >= 1000) {                               // 3  predicate
        shipcharge = amount * .06 + rushCharge;         // 4
    } else if (amount >= 200) {                         // 5  predicate
        shipcharge = amount * .08 + rushCharge;         // 6
    } else if (amount >= 100) {                         // 7  predicate
        shipcharge = 13.25 + rushCharge;                // 8
    } else if (amount >= 50) {                          // 9  predicate
        shipcharge = 9.95 + rushCharge;                 // 10
    } else if (amount >= 25) {                          // 11 predicate
        shipcharge = 7.25 + rushCharge;                 // 12
    } else {
        shipcharge = 5.25 + rushCharge;                 // 13
    }
    total = amount + tax + shipcharge;                  // 14
    return total;
}
```

The basis set has 7 paths, and each gets a test case:

| Case | Path | Input (nextday, amount) | Expected total |
|---|---|---|---|
| 1 | 1-2-3-4-14 | yes, 1500 | 1713.25 |
| 2 | 1-2-3-5-6-14 | yes, 300 | 360.25 |
| 3 | 1-2-3-5-7-8-14 | yes, 120 | 156.45 |
| 4 | 1-2-3-5-7-9-10-14 | yes, 90 | 120.975 |
| 5 | 1-2-3-5-7-9-11-12-14 | yes, 40 | 64.65 |
| 6 | 1-2-3-5-7-9-11-13-14 | yes, 10 | 30.475 |
| 7 | 1-3-4-14 | no, 1300 | 1472.25 |

(The slides round cases 4 and 6 to cents.) Checking case 1: rush = 14.50, tax = 1500 × 0.0725 = 108.75, ship = 1500 × 0.06 + 14.50 = 104.50, so the total is 1500 + 108.75 + 104.50 = **1713.25**.

<Callout type="warning" title="A real comparison bug">
  In Java, <code>nextday == "yes"</code> compares <strong>references</strong>, not text, so it can be false even when <code>nextday</code> holds "yes". Use <code>"yes".equals(nextday)</code>. This is exactly the kind of <strong>comparison error</strong> that unit testing should catch.
</Callout>

The basis-path tests become an automated unit test (here a Python port, with pytest):

```python title="test_shipping.py"
import pytest

def calculate(amount, nextday):
    rush = 14.50 if nextday == "yes" else 0
    tax = amount * 0.0725
    if amount >= 1000:
        ship = amount * 0.06 + rush
    elif amount >= 200:
        ship = amount * 0.08 + rush
    elif amount >= 100:
        ship = 13.25 + rush
    elif amount >= 50:
        ship = 9.95 + rush
    elif amount >= 25:
        ship = 7.25 + rush
    else:
        ship = 5.25 + rush
    return amount + tax + ship

@pytest.mark.parametrize("nextday, amount, expected", [
    ("yes", 1500, 1713.25),   # path 1-2-3-4-14
    ("yes", 300, 360.25),     # path 1-2-3-5-6-14
    ("yes", 120, 156.45),     # path 1-2-3-5-7-8-14
    ("yes", 90, 120.975),     # path 1-2-3-5-7-9-10-14
    ("yes", 40, 64.65),       # path 1-2-3-5-7-9-11-12-14
    ("yes", 10, 30.475),      # path 1-2-3-5-7-9-11-13-14
    ("no", 1300, 1472.25),    # path 1-3-4-14
])
def test_basis_paths(nextday, amount, expected):
    assert calculate(amount, nextday) == pytest.approx(expected)
```

## Integration and system testing

<SlideFigure page={24} caption="The full map: development testing (unit, integration, system), release testing (scenario, recovery, security) and user testing (alpha, beta)." />

### Integration testing

When modules are **combined**, check that they **interact correctly**. There are two views:

| Black-box view | White-box view |
|---|---|
| Validates **interfaces** and external behaviour | Checks **how modules connect internally** |
| No need to know the code | Tests data flow and code-level interactions |
| The user view: given **inputs**, do we get the **expected outputs**? | The developer view: do modules use the right **calls and data formats**? |

### System testing

All components are **integrated**, and the system is tested **as a whole**. System testing checks that components are **compatible**, **interact correctly** and **transfer the right data at the right time** across their interfaces. The software is also combined with the other system elements (hardware, people, information) for integration and validation tests.

## Release testing

Release testing differs from system testing in two ways:

| System testing | Release testing |
|---|---|
| Done by the **development team** | Done by a **separate team** that wasn't involved in development |
| Aims to **discover bugs** (**defect testing**) | Aims to show the system **meets its requirements** and is good enough for external use (**validation testing**) |

| Type | What it does |
|---|---|
| **Scenario testing** | Tests realistic **stories** of how users will use the system day to day. Use-case scenarios can be reused |
| **Recovery testing** | **Forces the software to fail** in various ways, and checks that recovery (re-initialization, data recovery, restart) happens correctly and within the required time |
| **Security testing** | Checks that the built-in **protection mechanisms** really stop improper access |

## User testing

Users or customers test the system and give feedback. This matters because the **real working environment** can't be fully replicated by developers.

<Grid cols={2}>
  <Card title="Alpha testing" tag="developer's site">
    Done by customers <strong>at the developer's site</strong>, under the developer's supervision. The developer "looks over the user's shoulder", recording errors and usage problems.
  </Card>
  <Card title="Beta testing" tag="customer's site">
    Done by end users <strong>at their own sites</strong>: a "live" use the developer can't control. Users report problems at regular intervals; the developers fix them, then release to the whole customer base.
  </Card>
</Grid>

In custom systems, **acceptance testing** follows: the customer tests the system with their own data to decide whether to **accept** it from the developer.

<Takeaways>

- An **independent path** adds at least one new edge. A **basis set** has $V(G)$ paths and covers every statement and both outcomes of every condition, but it isn't unique.
- Write **one test case per independent path**, with forcing inputs and expected outputs. Automate them.
- **Integration** testing checks that modules interact (black-box or white-box view). **System** testing tests the integrated whole.
- **Release** testing is done by a separate team to validate the requirements: **scenario**, **recovery** and **security** testing.
- **User** testing: **alpha** at the developer's site, **beta** live at the customer's sites.

</Takeaways>
