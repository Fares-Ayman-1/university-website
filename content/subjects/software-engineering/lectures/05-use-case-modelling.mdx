## System modelling

<Definition term="System modelling">
  Developing <strong>abstract models</strong> of a system, each presenting a different <strong>view or perspective</strong> of it, usually in a graphical notation based on the <strong>UML</strong>.
</Definition>

Models are used:

- **during requirements engineering**, to help derive the requirements;
- **during design**, to describe the system to the engineers who implement it;
- **after implementation**, to document the system's structure and operation.

### UML diagram types

<SlideFigure page={5} caption="The 13 UML diagram types: six structural and seven behavioural." />

| Structural (static structure) | Behavioural (dynamic behaviour) |
|---|---|
| **Class**, Object, Component, Composite structure, Deployment, Package | **Use case**, **Sequence**, **Activity**, **State machine**, Communication, Interaction overview, Timing |

This course focuses on the **use case**, **activity**, **state**, **sequence** and **class** diagrams.

## Use case diagrams

Use case modelling supports **requirements elicitation**: it describes what a user expects from the system, from the **user's perspective**. It is a common language for developers and users to agree on the system's functions.

<SlideFigure page={9} caption="Use case diagram elements: actor (stick figure), use case (oval), association (line), note, and dashed line attaching a note." />

| Element | Notation | Meaning |
|---|---|---|
| **Actor** | Stick figure | Anyone or anything **outside** the system that interacts with it: a person, group, organization or another system |
| **Use case** | Oval with a name | Something the system should **do** for an actor, a task |
| **Association** | Solid line | An actor takes part in a use case |
| **System boundary** | Rectangle around the use cases | The **scope** of the system: use cases inside, actors outside. Optional, but useful for complex systems with subsystems |
| **Note** | Rectangle with a folded corner, attached by a dashed line | Clarifies an aspect or task |

<SlideFigure page={11} caption="Student administration: the Professor actor can query student data, issue certificates and announce exams." />

To build a diagram, ask three questions: **What** is being described? (the system) **Who** interacts with it? (the actors) **What can they do?** (the use cases)

### Primary and secondary actors

| Primary actor | Secondary actor |
|---|---|
| **Initiates** the use case | **Helps** the primary actor complete it |
| Gets a **direct benefit** from it | Gets **no direct benefit** |
| "Who starts it?" | "Who assists or provides a service?" |

Actors can be **human** (Student, Professor) or **non-human** (an e-mail server, a bank system).

<SlideFigure page={15} caption="ATM: the ATM Customer is the primary actor (withdraw, query, transfer); the Operator is a secondary actor (add cash, startup, shutdown)." />

## Use case descriptions

A use case diagram is a simple overview. It **doesn't show the order** in which use cases run, and it is **implementation-independent**. Give the details as a **textual flow of events**, a **structured table**, or a **sequence diagram**. A description contains at least:

| Part | Content |
|---|---|
| **Use case** | Identifier and name |
| **Initiator** | The actor who starts it |
| **Goal** | A short description of what it achieves |
| **Pre-condition(s)** | What must hold **before** it can run |
| **Post-condition(s)** | What holds **after** it completes |
| **Main success scenario** | The numbered steps normally followed to reach the goal |

```text title="Use case: make reservation (hotel system)"
Identifier and name  make reservation
Initiator            Guest or Receptionist
Goal                 A room in a hotel is reserved for a guest.
Precondition         None.
Postcondition        A room of the desired type is reserved for the guest for the
                     requested period, and is no longer free for that period.
Assumptions          The guest uses a web browser, or the receptionist does it for
                     them; the guest is not yet known to the hotel system.

Main success scenario
1. The guest/receptionist chooses to make a reservation.
2. The guest/receptionist selects the hotel, dates and type of room.
3. The hotel system provides the availability and price (an offer is made).
4. The guest/receptionist agrees to proceed with the offer.
5. The guest/receptionist provides identification and contact details.
6. The guest/receptionist provides payment details.
7. The hotel system creates a reservation and gives it an identifier.
8. The hotel system reveals the identifier to the guest/receptionist.
9. The hotel system creates a confirmation and sends it to the guest.
```

### Scenarios

A **scenario** is **one instance** of a use case: a particular sequence of interactions. Each use case has a set of possible scenarios. For **borrow book**:

- a member with no outstanding loans borrows a book → **success** (the main success scenario);
- a member who has exceeded the loan quota tries to borrow → **refused**.

Same goal, different circumstances and outcome.

## Use case relationships

| Relationship | Between | Notation |
|---|---|---|
| **Association** | Actor ↔ use case only | Solid line |
| **Include** | Use case → use case | Dashed arrow labelled «include», from the **base** to the **included** case |
| **Extend** | Use case → use case | Dashed arrow labelled «extend», from the **extending** case to the **base** |
| **Generalization** | Actor → actor, or use case → use case | Solid line with a **hollow triangle** pointing to the parent |

### «include»

The behaviour of the **included** use case is always integrated into the **base** use case, which needs it in order to do its job. Use it to factor out **common behaviour** shared by several use cases.

<SlideFigure page={24} caption="«include» examples: Deposit Funds and Withdraw Cash both include Customer Authentication." />

### «extend»

The **extending** use case adds **optional or conditional** behaviour to a **base** use case at defined **extension points**.

- The extending use case **depends on** the base; the base must be **meaningful on its own**.
- The extension is usually **optional**. Attach a **note with the condition** saying when it happens.

<SlideFigure page={28} caption="«extend»: View Order History is optional; Refuse Loan extends Borrow Copy of Book only when the member has the maximum number of books." />

<Callout type="tip" title="Remember the arrow directions">
  «include» points <strong>from the base to the included</strong> case ("the base needs it"). «extend» points <strong>from the extension to the base</strong> ("I extend you, sometimes"). Example: <em>Sneeze</em> «include» <em>Close eyes</em> (it always happens), while <em>Say "Excuse me"</em> «extend» <em>Sneeze</em> (only sometimes).
</Callout>

### Generalization of actors

When actors share use cases, a **sub-actor inherits** every use case of its **super-actor** (an "is a" relationship). If actor A inherits from B, A can use B's use cases plus its own, but B can only use its own. Multiple inheritance is allowed.

<SlideFigure page={34} caption="Left: Professor AND Assistant are both needed to query student data. Right: an abstract Research Associate super-actor means a Professor OR an Assistant can query it." />

An **abstract actor** (`{abstract}`) groups the common properties of its sub-actors; only its sub-actors take part in practice.

### Generalization of use cases

If use case A generalizes B, then **B inherits A's behaviour** (and may extend or override it) and inherits all of A's relationships. An **abstract** use case (`{abstract}`) **can't be executed directly**; only its specializations can.

<SlideFigure page={36} caption="Announce event is abstract; Announce talk and Announce lecture specialize it." />

<Takeaways>

- **System models** give different views of a system; most use **UML** (6 structural + 7 behavioural diagrams).
- A **use case diagram** shows **actors** (outside), **use cases** (inside) and the **system boundary**.
- A **primary** actor starts the use case and benefits; a **secondary** actor helps.
- Describe each use case textually: **initiator, goal, pre/post-conditions, main success scenario**. A **scenario** is one instance.
- **«include»**: always, base → included. **«extend»**: optional or conditional, extension → base. **Generalization**: inheritance between actors or between use cases.

</Takeaways>

## Practice

<Exercise title="Library use cases" level="medium">

A library system lets **members** search the catalogue and borrow and return books. Borrowing and returning both require the **librarian** to log in. If a member returns a book late, the system **charges a fine**. Identify the actors, the use cases and the relationships.

<Solution>

- **Actors**: Member (primary for search, borrow and return) and Librarian (who records loans and returns, and logs in).
- **Use cases**: Search catalogue, Borrow book, Return book, Log in, Charge fine.
- **Relationships**:
  - Borrow book «include» Log in, and Return book «include» Log in. This is common, always-required behaviour.
  - Charge fine «extend» Return book, with the condition note *[book returned after due date]*.

</Solution>

</Exercise>

<Exercise title="Include or extend?" level="easy">

Choose the right relationship:

1. Every online payment must verify the card.
2. While placing an order, a customer may apply a discount coupon.
3. Both "transfer money" and "pay bill" need the user to be authenticated.

<Solution>

1. Make payment «include» Verify card (it always happens).
2. Apply coupon «extend» Place order (optional).
3. Transfer money «include» Authenticate, and Pay bill «include» Authenticate (shared behaviour).

</Solution>

</Exercise>
