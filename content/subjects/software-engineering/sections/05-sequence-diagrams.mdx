## Symbols

A sequence diagram is an **interaction diagram**: it shows the **flow of messages** between objects, with **time running downwards**. It gives a precise description of activities, and it is a good basis for designing and implementing communication.

<SlideFigure page={3} caption="Symbols: actor, lifeline (:User), option/loop frame, and alternative frame with a dashed line between the alternatives." />

| Symbol | Meaning |
|---|---|
| **Actor** (stick figure) | A role outside the system that interacts with it |
| **Lifeline** | A named rectangle (`:Class` or `name:Class`) with a dashed line below for the object's life |
| **Activation** (execution) | A thin rectangle on the lifeline: the object is **executing**, **sending a signal** or **waiting for a reply** |
| **opt / loop frame** | Messages that happen only **if** a condition holds, or **repeatedly** |
| **alt frame** | **Mutually exclusive** choices, separated by a dashed line, each with a guard |

## Message types

| Message | Arrow | Meaning |
|---|---|---|
| **Synchronous** | Solid line, **filled** arrowhead | The sender **waits** for a response; show both the call and the reply |
| **Asynchronous** | Solid line, **open** (lined) arrowhead | The sender **doesn't wait**; only the call is shown |
| **Reply** | **Dashed** line, open arrowhead | The answer to a call |
| **Create** | **Dashed** line labelled «create» | **Creates** a new object; its lifeline starts there |
| **Delete** | Solid line ending in an **X** on the lifeline | **Destroys** an object |
| **Self** | An arrow back to the same lifeline | An object calls its own operation |

## From use case to sequence diagram

<Steps>

1. Take the **use case text**: the numbered steps of one scenario.
2. Take the **class diagram**: the objects that will appear as lifelines.
3. Put the **initiating actor** on the left, then the lifelines in the order they are first used.
4. Turn **each step into one or more messages**, top to bottom. Use synchronous calls with replies where an answer is needed.
5. Add an **alt** frame for each "if/otherwise", and a **loop** for repeated steps.

</Steps>

### Example: buying a product online

```text title="Use case: Buy a Product Online"
1. Customer browses the catalogue and selects items to buy.
2. Customer goes to checkout.
3. Customer fills out the shipping information.
4. System presents the full pricing information, including shipping.
5. Customer fills in the credit card information.
6. System authorizes the purchase.
7. System confirms the sale immediately.
8. System sends a confirming email to the customer.
```

<SlideFigure page={15} caption="Sequence diagram for online shopping: Customer, Browse Interface, Item DB, Purchase Interface, Checkout and Credit Card Authorization." />

| Step | Message(s) |
|---|---|
| 1 | Customer → Browse Interface: `browseItems()`; Browse Interface → Item DB: `searchItems()`; Customer: `selectItem()` |
| 2–3 | Customer → Purchase Interface: `purchase()`, then shipping details |
| 4 | Purchase Interface → Customer: `displayPricingInfo()` (a reply) |
| 5–6 | Customer → Checkout: credit card info; Checkout → Credit Card Authorization: `authorizeCredit()` and its reply |
| 7–8 | Checkout → Customer: `confirmSale()`, then a confirming email (asynchronous) |

### Example: a medical system with an alt frame

<SlideFigure page={13} caption="View patient information: the receptionist calls ViewInfo(PID) on PatientInfo, which asks the MHCPMS-DB for a report; the DB checks Authorization; alt [Authorization OK] returns the patient info, [Authorization fail] returns Error (No Access)." />

The **alt** frame maps directly to `if/else` in code:

```python title="The medical-system sequence as code"
class Authorization:
    def authorize(self, info, uid):
        return uid in {"dr_ali", "nurse_mona"}          # who may see patient data

class PatientDB:
    def __init__(self, auth):
        self.auth = auth
        self.records = {"P17": "Patient 17: next visit 2026-11-02"}
    def report(self, info, pid, uid):
        if self.auth.authorize(info, uid):               # alt [Authorization OK]
            return self.records[pid]
        return "Error (No Access)"                       # alt [Authorization fail]

class PatientInfo:
    def __init__(self, db):
        self.db = db
    def view_info(self, pid, uid):                       # synchronous call from the actor
        return self.db.report("info", pid, uid)          # waits for the reply

p = PatientInfo(PatientDB(Authorization()))
print(p.view_info("P17", "dr_ali"))     # Patient 17: next visit 2026-11-02
print(p.view_info("P17", "visitor"))    # Error (No Access)
```

<Callout type="tip" title="Common mistakes">
  Don't connect two lifelines with a message that has no operation name. Every synchronous call needs an <strong>activation bar</strong> on the receiver. Keep <strong>one scenario per diagram</strong>, and use <code>alt</code>/<code>opt</code> instead of drawing several diagrams for small variations. Messages go downwards: a later message is never drawn above an earlier one.
</Callout>

<Takeaways>

- Lifelines are `:Class` boxes with dashed lines; **activations** show when an object is busy.
- **Synchronous** (filled head, wait for the dashed reply), **asynchronous** (open head), **create** (dashed «create»), **delete** (X), **self**.
- **alt** = if/else, **opt** = if, **loop** = repeat.
- Build the diagram from the **use case steps** (messages) plus the **class diagram** (lifelines).

</Takeaways>

## Practice

<Exercise title="Library: borrow a book" level="medium">

Use case steps: the member gives the book and card to the librarian; the librarian scans the card; the system checks the member's loans; **if** the member has fewer than 3 loans the system records the loan and prints a due-date slip; **otherwise** it shows "limit reached". List the lifelines and messages, with an alt frame.

<Solution>

**Lifelines**: `Member` (actor), `Librarian` (actor), `:LoanSystem`, `:MemberDB`, `:Printer`.

1. Member → Librarian: hand over the book and card.
2. Librarian → :LoanSystem: `scanCard(memberId)`, `scanBook(bookId)`.
3. :LoanSystem → :MemberDB: `countLoans(memberId)`, with the reply `n`.
4. **alt**:
   - `[n < 3]`: :LoanSystem → :MemberDB: `recordLoan(memberId, bookId)`; :LoanSystem → :Printer: `printSlip(dueDate)` (asynchronous); reply "done" to the Librarian.
   - `[else]`: :LoanSystem → Librarian: `showMessage("limit reached")`.

</Solution>
