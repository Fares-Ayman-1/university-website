## What a state diagram shows

A state diagram presents the **states an object can be in**, the **transitions** between them, and where the sequence of state changes **starts and ends**. For example:

- a light switches from *Off* to *On*;
- a TV changes channel when you press the remote;
- after some time a washing machine goes from *Washing* to *Rinsing*;
- a project is *submitted, evaluated, accepted, rejected, monitored, audited, finished, delayed*.

<Callout type="note" title="One object, not many">
  The diagrams you've studied so far model a <strong>group</strong> of classes, objects or use cases. A state diagram shows the states of <strong>a single object</strong> (one order, one car, one reservation) over its lifetime.
</Callout>

## Symbols

<SlideFigure page={4} caption="Start (filled circle), state (rounded rectangle), event (a labelled arrow between states) and a composite state with activities inside." />

<SlideFigure page={5} caption="Join (several states into one), fork (one state into several concurrent ones) and final state (bull's-eye)." />

| Symbol | Meaning |
|---|---|
| ● **Start** | The initial pseudo-state |
| ▭ **State** | A condition the object is in, named with an adjective or past participle (*Waiting*, *Confirmed*, *Repaired*) |
| → **Transition** | Labelled `event [guard] / action`: when the **event** happens and the **guard** is true, do the **action** and move |
| **Composite state** | A state that contains its own internal states or activities |
| **Fork / join** | Split into concurrent states, or wait for several to finish |
| ◉ **Final** | The object's life ends |

## Worked example: the car agency

> The customer **enters** the car, then the car's **papers are reviewed**, then the car is **investigated**. If the repair takes **one day**, the car is **queued**; if it takes **more than one day**, it is **stored in the garage**. It moves from the garage to the queue **when the repair day is today**. It moves from the queue to **customer check** after it is **repaired**. If the customer is **not satisfied**, it is queued again; if **satisfied**, it is **released**.

The **verbs** become events, the **"the car is …"** phrases become states, and the **"if …"** phrases become guards:

<SlideFigure page={9} caption="Entered → Reviewed → Car investigated → [num_of_days > 1] Stored in Garage → [repair = 1 day] Queued, or [num_of_days = 1] Queued directly → (Repair) Repaired → (Review) Customer Review → (Satisfied) Released → final; Not satisfied goes back to Queued." />

## Event / action labels: hotel reservation

A transition label can carry an **action** after the slash: what the system **does** during the transition.

<SlideFigure page={11} caption="Hotel reservation: event above the line, action below, e.g. 'room available / decrement room count'." />

| From | Event / action | To |
|---|---|---|
| Null | room request / none | Requested |
| Requested | room available / decrement room count | Confirmed |
| Requested | no room available / put on list | On waiting list |
| On waiting list | room available / decrement room count | Confirmed |
| On waiting list | customer gives up / remove from list | Canceled |
| Confirmed | customer cancels / increment room count | Canceled |
| Confirmed | customer moves in / none | Used |
| Used | customer pays / increment room count | Archived |

The table translates almost line by line into code:

```python title="reservation.py"
class Hotel:
    def __init__(self, rooms):
        self.rooms = rooms
        self.waiting_list = []

class Reservation:
    def __init__(self, hotel):
        self.hotel, self.state = hotel, "Null"

    def request(self):                                   # room request / none
        assert self.state == "Null"
        self.state = "Requested"
        self._try_confirm()

    def _try_confirm(self):
        if self.hotel.rooms > 0:                         # room available
            self.hotel.rooms -= 1                        #   / decrement room count
            if self in self.hotel.waiting_list:
                self.hotel.waiting_list.remove(self)
            self.state = "Confirmed"
        elif self.state == "Requested":                  # no room available
            self.hotel.waiting_list.append(self)         #   / put on list
            self.state = "On waiting list"

    def cancel(self):
        if self.state == "Confirmed":                    # customer cancels
            self.hotel.rooms += 1                        #   / increment room count
        elif self.state == "On waiting list":            # customer gives up
            self.hotel.waiting_list.remove(self)         #   / remove from list
        self.state = "Canceled"

    def move_in(self):                                   # customer moves in / none
        assert self.state == "Confirmed"
        self.state = "Used"

    def pay(self):                                       # customer pays
        assert self.state == "Used"
        self.hotel.rooms += 1                            #   / increment room count
        self.state = "Archived"

h = Hotel(rooms=1)
a, b = Reservation(h), Reservation(h)
a.request(); b.request()
print(a.state, "|", b.state)          # Confirmed | On waiting list
a.cancel(); b._try_confirm()          # a cancels, so a room is free again for b
print(a.state, "|", b.state)          # Canceled | Confirmed
b.move_in(); b.pay()
print(b.state, "| rooms:", h.rooms)   # Archived | rooms: 1
```

<Takeaways>

- A state diagram models **one object's** life: its **states**, the **events** that move it, the **guards** that must hold, and the **actions** done on the way.
- Label transitions **`event [guard] / action`**, and put **`entry/ do/ exit/`** activities inside states.
- From a problem text: **"the object is …"** gives states, **verbs/occurrences** give events, and **"if …"** gives guards.
- Each transition becomes a **method** that checks the current state, does the action and sets the new state.

</Takeaways>

## Practice

<Exercise title="Library book copy" level="medium">

A copy of a book is **Available** when added to the library. When a member borrows it, it becomes **On loan**. When it is returned it is **Available** again, unless it is **damaged**, in which case it goes to **Repair**, then back to Available when fixed. A copy on loan for more than 30 days is **Overdue**; returning it charges a fine. A copy can be **Withdrawn** (final) from Available or Repair. Write the transitions as `event [guard] / action`.

<Solution>

- initial → **Available**: `add copy`
- Available → **On loan**: `borrow / record loan`
- On loan → **Overdue**: `day passes [days on loan > 30]`
- On loan → **Available**: `return [not damaged]`
- Overdue → **Available**: `return [not damaged] / charge fine`
- On loan or Overdue → **Repair**: `return [damaged]`, with `/ charge fine` from Overdue
- Repair → **Available**: `fixed`
- Available or Repair → **Withdrawn**: `withdraw`, then → final.

</Solution>

</Exercise>
