## What a DFD shows

<Ar>ما يعرضه مخطط DFD</Ar>

<Definition term="Data flow diagram (DFD)" termAr="مخطط تدفق البيانات (DFD)">
  A picture of the <strong>movement of data</strong> between <strong>external entities</strong> and the <strong>processes</strong> and <strong>data stores</strong> within a system.

  <Ar>صورة تُبيِّن <strong>حركة البيانات</strong> بين <strong>الكيانات الخارجية (external entities)</strong> و<strong>العمليات (processes)</strong> و<strong>مخازن البيانات (data stores)</strong> داخل النظام.</Ar>
</Definition>

A DFD is **not** a UML diagram, and it is **not** a flowchart. It shows **what data goes where**, not the order of steps or the decisions. It has no loops, no conditions and no timing.

<Ar>مخطط DFD **ليس** مخطط UML، و**ليس** مخططًا انسيابيًا (flowchart). إنه يُبيِّن **أي البيانات تذهب إلى أين**، لا ترتيب الخطوات ولا القرارات. فلا توجد فيه حلقات تكرار، ولا شروط، ولا توقيت.</Ar>

## Symbols

<Ar>الرموز</Ar>

<SlideFigure page={3} caption="Process (a rounded box with a number on top) and data store (an open-ended rectangle)." captionAr="العملية (process): صندوق بزوايا مستديرة يعلوه رقم، ومخزن البيانات (data store): مستطيل مفتوح الطرف." />

| Symbol <Ar>الرمز</Ar> | Name <Ar>الاسم</Ar> | Meaning <Ar>المعنى</Ar> | Label <Ar>التسمية</Ar> |
|---|---|---|---|
| Rounded rectangle, numbered <Ar>مستطيل بزوايا مستديرة، مرقَّم</Ar> | **Process** <Ar>**العملية**</Ar> | Work done on data **inside** the system: it **transforms** incoming flows into outgoing flows <Ar>عمل يُجرى على البيانات **داخل** النظام: فهي **تحوِّل** التدفقات الداخلة إلى تدفقات خارجة</Ar> | A **verb phrase** and a **number**: *1.0 Verify Member* <Ar>**عبارة فعلية (verb phrase)** و**رقم**: `1.0 Verify Member`</Ar> |
| Open-ended rectangle <Ar>مستطيل مفتوح الطرف</Ar> | **Data store** <Ar>**مخزن البيانات**</Ar> | A repository of data (a file or database table) <Ar>مستودع للبيانات (ملف أو جدول في قاعدة بيانات)</Ar> | A **noun**: *Member File* <Ar>**اسم (noun)**: *Member File*</Ar> |
| Arrow <Ar>سهم</Ar> | **Data flow** <Ar>**تدفق البيانات**</Ar> | A pipeline that carries a packet of data <Ar>قناة تحمل حزمة من البيانات</Ar> | A **noun** for the data moving: *Order Form* <Ar>**اسم (noun)** للبيانات المنقولة: *Order Form*</Ar> |
| Square / rectangle <Ar>مربع / مستطيل</Ar> | **External entity** <Ar>**الكيان الخارجي**</Ar> | A **source or destination** outside the system <Ar>**مصدر أو وجهة** خارج النظام</Ar> | A **noun**: *Customer* <Ar>**اسم (noun)**: *Customer*</Ar> |

## Rules

<Ar>القواعد</Ar>

<SlideFigure page={6} caption="Rule 1: a process can have more than one incoming and more than one outgoing data flow." captionAr="القاعدة 1: يمكن أن يكون للعملية (process) أكثر من تدفق بيانات داخل، وأكثر من تدفق بيانات خارج." />

<Steps>

1. Every **process** has **at least one input and one output**. A process with only inputs is a "black hole"; one with only outputs is a "miracle".
   <Ar>لكل **عملية (process)** **مُدخَل واحد ومُخرَج واحد على الأقل**. والعملية التي لها مُدخَلات فقط تُسمّى «ثقبًا أسود» (black hole)، والتي لها مُخرَجات فقط تُسمّى «معجزة» (miracle).</Ar>
2. A process **transforms** data. Its outputs differ from its inputs, e.g. *Order* → *1.0 Verify Order* → *Accepted Order*.
   <Ar>العملية **تحوِّل** البيانات، فمُخرَجاتها تختلف عن مُدخَلاتها، مثل: `Order → 1.0 Verify Order → Accepted Order`.</Ar>
3. Data can't move **directly between two data stores**, **between two external entities**, or **between an entity and a store**. It must pass **through a process**.
   <Ar>لا يمكن أن تنتقل البيانات **مباشرةً بين مخزنَي بيانات (data stores)**، أو **بين كيانين خارجيين (external entities)**، أو **بين كيان ومخزن**، بل يجب أن تمر **عبر عملية (process)**.</Ar>
4. Every data flow has a **name** (a noun), and every process a **number** and a **verb phrase**.
   <Ar>لكل تدفق بيانات (data flow) **تسمية** تكون اسمًا (noun)، ولكل عملية **رقم** و**عبارة فعلية (verb phrase)**.</Ar>

</Steps>

<SlideFigure page={7} caption="Rule 2: a process transforms its input: Order → 1.0 Verify Order → Accepted Order → 2.0 Assemble Order → Inventory Change." captionAr="القاعدة 2: العملية تحوِّل مُدخَلها: الطلب (Order) ← العملية 1.0 التحقق من الطلب (Verify Order) ← الطلب المقبول (Accepted Order) ← العملية 2.0 تجميع الطلب (Assemble Order) ← تغيُّر المخزون (Inventory Change)." />

## Context diagram and level 0

<Ar>مخطط السياق والمستوى 0</Ar>

| Diagram <Ar>المخطط</Ar> | Shows <Ar>ما يعرضه</Ar> |
|---|---|
| **Context diagram** <Ar>**مخطط السياق**</Ar> | The **whole system as one process** (numbered 0), the **external entities** around it, and the flows between them. **No data stores** <Ar>**النظام كله كعملية واحدة** (رقمها 0)، و**الكيانات الخارجية (external entities)** المحيطة به، والتدفقات بينها. **بلا مخازن بيانات**</Ar> |
| **Level-0 diagram** (diagram 0) <Ar>**مخطط المستوى 0** (المخطط 0)</Ar> | The context's process **exploded** into the major processes (1.0, 2.0, 3.0…), now **with data stores** <Ar>عملية مخطط السياق بعد **تفجيرها (exploded)** إلى العمليات الرئيسية (1.0، 2.0، 3.0…)، وهذه المرة **مع مخازن البيانات**</Ar> |

<Callout type="note" title="Naming varies" titleAr="تختلف التسميات">
  Some books call the context diagram itself "level 0" and its first decomposition "level 1". The slides use both names. What matters is that every level is <strong>balanced</strong>: the flows into and out of a process must match the flows on its decomposition.

  <Ar>بعض الكتب تسمّي مخطط السياق نفسه «المستوى 0» (level 0)، وتسمّي أول تفكيك له «المستوى 1» (level 1). والشرائح تستخدم التسميتين. المهم أن يكون كل مستوى <strong>متوازنًا (balanced)</strong>: يجب أن تطابق التدفقاتُ الداخلة إلى العملية والخارجة منها التدفقاتِ الموجودة في تفكيكها.</Ar>
</Callout>

## Worked example: a mail-ordering system

<Ar>مثال محلول: نظام طلبات بالبريد</Ar>

> A mail-order company sells CDs and tapes at discount prices to its club **members**. When an order-processing clerk receives an **order form**, she **verifies that the sender is a member** by checking the **MEMBER FILE**. If not, she returns the order with a **membership application form**. If the customer is a member, she **verifies the order item data** by checking the **ITEM FILE**. Then she enters the order and saves it to the **DAILY ORDERS FILE**. At the same time she **prints an invoice and shipping list**, which go to the **ORDER FULFILLMENT DEPARTMENT**.

<Ar>تبيع شركة طلبات بالبريد أقراصًا مدمجة (CDs) وأشرطة بأسعار مخفّضة إلى **أعضاء** ناديها. وعندما تتلقّى موظفة معالجة الطلبات **نموذج طلب (order form)**، **تتحقق من أن المُرسِل عضو** بمراجعة **ملف الأعضاء (MEMBER FILE)**. وإن لم يكن عضوًا، تعيد الطلب مع **نموذج طلب عضوية (membership application form)**. وإن كان العميل عضوًا، **تتحقق من بيانات عناصر الطلب** بمراجعة **ملف العناصر (ITEM FILE)**. ثم تُدخِل الطلب وتحفظه في **ملف الطلبات اليومية (DAILY ORDERS FILE)**. وفي الوقت نفسه **تطبع فاتورة وقائمة شحن** تُرسَلان إلى **قسم تنفيذ الطلبات (ORDER FULFILLMENT DEPARTMENT)**.</Ar>

| In the text <Ar>في النص</Ar> | DFD element <Ar>عنصر مخطط DFD</Ar> |
|---|---|
| Customer, Order Fulfillment Department <Ar>العميل، وقسم تنفيذ الطلبات</Ar> | **External entities** <Ar>**كيانات خارجية**</Ar> |
| verifies member, verifies order items, prints invoice <Ar>التحقق من العضو، والتحقق من عناصر الطلب، وطباعة الفاتورة</Ar> | **Processes** 1.0, 2.0, 3.0 <Ar>**العمليات** 1.0، 2.0، 3.0</Ar> |
| MEMBER FILE, ITEM FILE, DAILY ORDERS FILE <Ar>ملف الأعضاء، وملف العناصر، وملف الطلبات اليومية</Ar> | **Data stores** <Ar>**مخازن بيانات**</Ar> |
| order form, application form, order data, invoice and shipping list <Ar>نموذج الطلب، ونموذج طلب العضوية، وبيانات الطلب، والفاتورة وقائمة الشحن</Ar> | **Data flows** <Ar>**تدفقات بيانات**</Ar> |

<SlideFigure page={12} caption="The context diagram: Customer → Order Form → 0 Mail Ordering System → Invoice and Shipping List → Order Processing Department; Application Form goes back to the Customer." captionAr="مخطط السياق: العميل (Customer) ← نموذج الطلب (Order Form) ← العملية 0 نظام الطلبات بالبريد (Mail Ordering System) ← الفاتورة وقائمة الشحن (Invoice and Shipping List) ← قسم معالجة الطلبات (Order Processing Department)؛ ونموذج طلب العضوية (Application Form) يعود إلى العميل." />

<SlideFigure page={11} caption="The level-0 diagram: 1.0 Verify Member (reads the Member File) → 2.0 Verify Order Item Data (reads the Item File, writes Daily Orders) → 3.0 Print Invoice and Shipping List → Order Processing Department." captionAr="مخطط المستوى 0: العملية 1.0 التحقق من العضو (Verify Member) وتقرأ ملف الأعضاء (Member File) ← العملية 2.0 التحقق من بيانات عناصر الطلب (Verify Order Item Data) وتقرأ ملف العناصر (Item File) وتكتب في الطلبات اليومية (Daily Orders) ← العملية 3.0 طباعة الفاتورة وقائمة الشحن (Print Invoice and Shipping List) ← قسم معالجة الطلبات (Order Processing Department)." />

Check the **balance**: the context has *Order Form* in, and *Application Form* and *Invoice and Shipping List* out. The level-0 diagram has exactly the same external flows.

<Ar>تحقّق من **التوازن (balance)**: في مخطط السياق يدخل *Order Form*، ويخرج *Application Form* و*Invoice and Shipping List*. ومخطط المستوى 0 فيه التدفقات الخارجية نفسها تمامًا.</Ar>

## Checking the rules automatically

<Ar>التحقق من القواعد تلقائيًا</Ar>

The rules are mechanical enough to check with a script. Here is the mail-ordering level-0 diagram as data:

<Ar>القواعد آلية بما يكفي للتحقق منها ببرنامج نصي (script). وهذا مخطط المستوى 0 لنظام الطلبات بالبريد ممثَّلًا كبيانات:</Ar>

```python title="dfd_check.py"
kind = {
    "Customer": "entity", "Order Dept": "entity",
    "1.0 Verify Member": "process", "2.0 Verify Items": "process",
    "3.0 Print Invoice": "process",
    "Member File": "store", "Item File": "store", "Daily Orders": "store",
}
flows = [  # (from, to, data)
    ("Customer", "1.0 Verify Member", "Order Form"),
    ("Member File", "1.0 Verify Member", "Member Info"),
    ("1.0 Verify Member", "Customer", "Application Form"),
    ("1.0 Verify Member", "2.0 Verify Items", "New Order"),
    ("Item File", "2.0 Verify Items", "Item Info"),
    ("2.0 Verify Items", "Daily Orders", "Validated Order"),
    ("2.0 Verify Items", "3.0 Print Invoice", "Validated Order"),
    ("3.0 Print Invoice", "Order Dept", "Invoice and Shipping List"),
]

def problems(kind, flows):
    found = []
    for a, b, data in flows:
        if "process" not in (kind[a], kind[b]):
            found.append(f"{a} -> {b}: data must pass through a process")
    for p in (n for n, k in kind.items() if k == "process"):
        if not any(b == p for _, b, _ in flows):
            found.append(f"{p}: no input (a miracle)")
        if not any(a == p for a, _, _ in flows):
            found.append(f"{p}: no output (a black hole)")
    return found

print(problems(kind, flows) or "valid DFD")
# valid DFD
print(problems(kind, flows + [("Customer", "Order Dept", "Complaint")]))
# ['Customer -> Order Dept: data must pass through a process']
```

<Takeaways>

- A DFD shows **data movement**, not control flow: no decisions, loops or timing.
  <Ar>يعرض مخطط DFD **حركة البيانات**، لا تدفق التحكم (control flow): فلا قرارات ولا حلقات تكرار ولا توقيت.</Ar>
- Four symbols: **process** (numbered verb phrase), **data store** (noun), **data flow** (named noun), **external entity** (source or sink).
  <Ar>أربعة رموز: **العملية (process)** (عبارة فعلية مرقَّمة)، و**مخزن البيانات (data store)** (اسم)، و**تدفق البيانات (data flow)** (يُسمّى باسم)، و**الكيان الخارجي (external entity)** (مصدر أو مَصَبّ).</Ar>
- Every process needs **input and output**, and all data moves **through processes**, never store-to-store or entity-to-entity.
  <Ar>كل عملية تحتاج إلى **مُدخَل ومُخرَج**، وكل البيانات تنتقل **عبر العمليات**، ولا تنتقل أبدًا من مخزن إلى مخزن أو من كيان إلى كيان.</Ar>
- Start with a **context diagram** (one process, no stores), then **explode** it into level 0, keeping the levels **balanced**.
  <Ar>ابدأ **بمخطط السياق (context diagram)** (عملية واحدة، بلا مخازن)، ثم **فجِّره (explode)** إلى المستوى 0، مع الحفاظ على **توازن** المستويات.</Ar>

</Takeaways>

<Exercise title="Find the errors" titleAr="اكتشف الأخطاء" level="easy">

What is wrong with each of these DFD fragments?

<Ar>ما الخطأ في كل جزء من أجزاء مخططات DFD التالية؟</Ar>

1. *Customer* → *Supplier*, labelled "Order".
   <Ar>من العميل (*Customer*) إلى المورِّد (*Supplier*)، بالتسمية «Order» (طلب).</Ar>
2. *Item File* → *Daily Orders*, labelled "Items".
   <Ar>من ملف العناصر (*Item File*) إلى الطلبات اليومية (*Daily Orders*)، بالتسمية «Items» (عناصر).</Ar>
3. Process *4.0 Archive Records* has only incoming flows.
   <Ar>العملية `4.0 Archive Records` لها تدفقات داخلة فقط.</Ar>
4. A data flow with no label.
   <Ar>تدفق بيانات (data flow) بلا تسمية.</Ar>

<Solution>

1. Entity-to-entity: the data must pass through a process, e.g. *Place Order*.
   <Ar>من كيان إلى كيان: يجب أن تمر البيانات عبر عملية (process)، مثل *Place Order* (تقديم الطلب).</Ar>
2. Store-to-store: a process must move the data.
   <Ar>من مخزن إلى مخزن: يجب أن تنقل عمليةٌ البيانات.</Ar>
3. A black hole: a process must also produce output.
   <Ar>ثقب أسود (black hole): يجب أن تُنتج العملية مُخرَجات أيضًا.</Ar>
4. Every data flow must be named with the data it carries.
   <Ar>يجب أن يُسمّى كل تدفق بيانات باسم البيانات التي يحملها.</Ar>

</Solution>

<Exercise title="Restaurant ordering DFD" titleAr="مخطط DFD لطلبات مطعم" level="medium">

A **customer** gives an order to the **waiter**. The system **records the order** in the ORDERS file and sends it to the **kitchen**. When the food is ready, the system **produces a bill** using the MENU file (prices). The customer pays, and the system **records the payment** in the PAYMENTS file. Draw the context diagram and the level-0 diagram as lists.

<Ar>يُعطي **العميل** طلبه إلى **النادل**. ويقوم النظام **بتسجيل الطلب** في الملف ORDERS ويرسله إلى **المطبخ**. وعندما يجهز الطعام، **يُصدر النظام فاتورة** باستخدام الملف MENU (الأسعار). ويدفع العميل، فيقوم النظام **بتسجيل الدفعة** في الملف PAYMENTS. ارسم مخطط السياق (context diagram) ومخطط المستوى 0 في صورة قوائم.</Ar>
